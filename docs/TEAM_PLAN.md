## 1. 分工原則

1. **按模組切，不按階段切**：不是「A 做研究、B 寫程式、C 做簡報」，而是每個人都寫程式、都有一塊研究內容、都上台講自己那段。
2. **一個模組一個負責人**：負責人實作並做最後決定，另一人負責審查。
3. **介面先行**：第 2 週結束前凍結 `types.py` 和函式簽名（見 ARCHITECTURE.md），之後用假模組平行開發。
4. **每人一個橫向職責**：避免「整合、實驗、文件」變成沒人管的事。
5. **口試可以分段講**：分工對應期末簡報的章節，每個人都能講清楚自己的模組並回答相關問題。

## 2. 角色定義

### A — AI 與評估

| 項目 | 內容 |
|---|---|
| 主模組 | `segmenter.py`、`edge.py`、`fusion.py`、`eval/metrics.py` |
| 橫向職責 | 資料集管理、ROI 標準答案、實驗腳本與結果圖表 |
| 研究內容 | 語意先驗的品質與限制（VOC 類別問題）、α/β 敏感度分析、評估方法是否正確（避免循環評估） |
| 口試負責章節 | 04 AI 模組、08 消融實驗、09 評估、10 敏感度分析 |
| 適合的人 | 對 PyTorch、資料分析、畫圖有興趣 |

### B — 核心演算法

| 項目 | 內容 |
|---|---|
| 主模組 | `weighted_vq.py`、`dither.py`、`datasets/make_synthetic.py` |
| 橫向職責 | 數學正確性（推導、證明 J 單調遞減）、效能優化（Numba、向量化） |
| 研究內容 | 權重如何影響群中心（簡報第 6 頁備註的問題）、初始化策略、空群處理、收斂行為、邊緣保護的 γ |
| 口試負責章節 | 02 問題定義、05 核心演算法、06 的抖色部分 |
| 適合的人 | 喜歡數學、演算法、效能調校 |

### C — 編解碼與產品

| 項目 | 內容 |
|---|---|
| 主模組 | `rq_codec.py`、`pipeline.py`、`cli.py`、`viz.py`、`app/` |
| 橫向職責 | 建 repo、持續整合、環境（uv）、整合（協調合併衝突）、展示與展場 |
| 研究內容 | `.rq` 格式設計、實際 bpp 與理論值的差異、（延伸）熵編碼 X1 和 PNG-8/GIF 比較 X5 |
| 口試負責章節 | 03 系統架構、06 編解碼、07 產品、12 實作、現場展示 |
| 適合的人 | 喜歡系統、工程、介面 |

### 共同責任

- 文獻回顧：每人負責自己模組相關的 2～3 篇
- ROI 人工標註（若採用）：三人平分 Kodak 24 張，互相檢查
- 期末報告：每人寫自己模組的章節；A 統整實驗章節、C 統整系統章節、B 統整方法章節
- 程式碼審查：每個 PR 至少要有一位非作者核准

> 這只是建議的分配。如果三人興趣不同，換人沒問題，**但建議保留「一模組一負責人 + 一個橫向職責」的結構**。見 `DISCUSSION.md` 第 1 題。

```
│  ├─ 2.1 載入分割模型 + semantic_map + 縮放回原尺寸 [2]

├─ 3. 核心演算法 (B)

│  ├─ 3.4 分塊分配 + 色票轉回 uint8 [0.5]

│  ├─ 4.1 檔頭結構、encode/decode [1]
│  ├─ 4.2 通用位元打包（b=1～8）[1]
│  ├─ 4.3 還原測試（所有 K、奇數寬高、hypothesis）（AC-2）[1]
│  ├─ 4.4 actual_bpp、reconstruct [0.5]
│  ├─ 4.5 cli.py：encode/decode/eval [1]
│  └─ 4.6 viz.py：熱圖、色票色塊、並排比較圖 [1]

│  ├─ 5.2 決定 ROI 標準答案方案（DISCUSSION 第 4 題）並取得或標註 [2～4，若人工標註則三人分攤]
```

**粗估工作量**（不含第 8 項交付與延伸項目）：A 約 17、B 約 13、C 約 15 人日。B 比較少，是因為第 3 項的除錯和數學推導常常超出估計，而且 B 還要支援 6.5 和延伸項目。如果實際上不平均，在每週會議調整。

```
0.4 介面凍結 ──┬──► 1.x 假模組骨架 ──► 7.1 工作室骨架 ─────────────────► 7.x 工作室完成

               │                                      │          │
               ├──► 4.1～4.3 編解碼 ──────────────────┘     5.1 指標 + 5.2 ROI 標準答案
               │
```

- **3.3 加權 Lloyd** 和 **5.2 ROI 標準答案** 最容易拖延，要最先開始、卡住就最先求救。

## 7. 協作節奏

### 7.1 每週

| 時間 | 活動 | 長度 | 產出 |
|---|---|---|---|
| 週一（或固定某天） | **每週會議**（三人） | 30～45 分鐘 | 更新任務板，決策寫進 `docs/DECISIONS.md` |
| 平日 | 非同步：GitHub Issue／PR 討論 + 通訊軟體群組 | — | PR、審查 |
| 週末前 | 每人在群組貼三行**週報**：完成了什麼／下週做什麼／卡在哪 | 5 分鐘 | 讓其他人知道進度 |

**每週會議固定議程**
1. 每人 2 分鐘：上週完成、本週計畫、卡在哪裡
2. 看任務板：有沒有卡超過一週的 Issue
3. 需要決定的事 → 決定後寫進 `DECISIONS.md`
4. 展示新功能（從 M2 開始每週都能跑工作室）

### 7.2 卡關規則

- 自己卡超過**半天**就在群組問；卡超過**兩天**就在會議上重新分配或簡化。

### 7.3 決策紀錄

建立 `docs/DECISIONS.md`，每條格式如下：

```
## D-003  ROI 標準答案來源（2026-xx-xx）
- 決定：...
- 考慮過的選項：...
- 理由：...
- 影響文件：SPEC §6.1、EXPERIMENTS §3
```

## 8. 風險與對策

| 編號 | 風險 | 可能性 | 對策 |
|---|---|---|---|
| R1 | Kodak 很多張沒有 VOC 物件 → S 幾乎全 0，方法看不出效果 | 高 | 第 3 週就先統計（任務 2.2）；加入有物件的資料集；X4 顯著性模型當備案；寫成誠實限制 |
| R2 | 方法沒有贏過基準組 | 中 | 研究問題本來就是「是否穩定改善」；負面結果加上分析一樣是貢獻；看 ROI 指標，不只看全圖 |
| R3 | 加權 VQ 有不容易發現的錯誤 | 中 | AC-1 和 sklearn 對照；J 單調性測試；用答案已知的合成影像測試 |
| R4 | ROI 人工標註太花時間 | 中 | 三人分攤；或改用有標準答案的公開資料集 |
| R5 | 抖色太慢 | 低 | 用 Numba；展示時把長邊縮到 768 |
| R6 | 整合衝突、環境不一致 | 中 | uv.lock、持續整合、介面凍結、PR 保持小 |
| R7 | 有人進度落後、考試週 | 高 | 預留緩衝（第 12～13 週）；關鍵路徑任務優先；考試週前一週減量 |
| R8 | 展場網路或電腦出問題 | 中 | 在本機執行、不依賴網路；準備備案影片和預先算好的範例 |
| R9 | 資料授權問題 | 低 | 寫在 MANIFEST；SIPI 逐張確認；不寫「零法規風險」 |
